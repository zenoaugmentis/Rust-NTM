# S08 · Ручная проверка ItemStack, инвентарей и legacy NBT

Проверку выполнил Zeno на Windows и PowerShell 20 ноября 2026 года. [Задача #21](https://github.com/zenoaugmentis/horizon-NTM/issues/21).

## 1. Эталон

| Компонент | Локальный JAR | SHA-1 |
| --- | --- | --- |
| Ванильный клиент 1.7.10 | `versions/1.7.10/1.7.10.jar` | `E80D9B3BF5085002218D4BE59E668BAC718ABBC6` |
| Ванильный сервер 1.7.10 | `server-vanilla/minecraft_server.1.7.10.jar` | `952438AC4E01B4D115C5FC38F891710C4941DF29` |

Оба SHA-1 совпали с [эталоном S01](../specs/versions.md). Проверка Forge выполнена в профиле 1.7.10 / 10.13.4.1614 с установленным OpenComputers. Версию JAR OpenComputers отдельно не зафиксировал. Для чтения NBT использовал Python и `nbtlib`.

## 2. Ванильный инвентарь и поля ItemStack

Создал одиночный мир `S08-vanilla-items`. Выдал себе 10 красной шерсти `/give @p minecraft:wool 10 14 {display:{Name:"S08-Red"}}` и железную кирку `/give @p minecraft:iron_pickaxe 1 37`. Положил их в первые две ячейки панели быстрого доступа и сохранил мир. В игре у кирки оставалась полная прочность минус 37.

Прочитал `Data.Player.Inventory` из `level.dat`:

```text
{Slot: 0b, id: 35s, Count: 10b, tag: {display: {Name: "S08-Red"}}, Damage: 14s}
{Slot: 1b, id: 257s, Count: 1b, Damage: 37s}
```

| Поле | Тип NBT | Фактическое значение |
| --- | --- | --- |
| `Slot` | Byte | `0` для первой ячейки и `1` для второй |
| `id` | Short | `35` у шерсти и `257` у кирки |
| `Count` | Byte | `10` и `1` |
| `Damage` | Short | `14` задаёт цвет шерсти, `37` задаёт износ кирки |
| `tag` | Compound, необязательный | У шерсти содержит `display.Name`, у кирки отсутствует |

## 3. Разделение, слияние и предел стека

Переключился в выживание. После каждого изменения сохранял мир и повторно читал `Data.Player.Inventory`, если в таблице указан результат NBT.

| Проверка | Действие | Наблюдение |
| --- | --- | --- |
| Разделение | Правый клик по 10 шерсти, перенос половины в третью ячейку | В слотах `0` и `2` по 5. У обеих частей совпали `id=35s`, `Damage=14s` и `tag.display.Name="S08-Red"`. |
| Слияние одинаковых стеков | Левый клик стеком из слота `2` по стеку в слоте `0` | В слоте `0` снова 10 с исходным тегом. Запись слота `2` исчезла. |
| Разный цвет | 3 синих `S08-Red` с `Damage=11` против 10 красных `S08-Red` с `Damage=14` | В GUI стеки поменялись местами. |
| Разное имя | 4 красных `S08-Other` против 10 красных `S08-Red` | В GUI стеки поменялись местами. |
| Предел шерсти | К 10 красным `S08-Red` добавил ещё 60 через `give` | После подбора в слоте `0` сохранилось 64, в слоте `4` — 6. Контрольные стеки остались отдельными. |
| Предел пустого ведра | Выдал 17 через `/give @p minecraft:bucket 17` | После подбора ID `325` записался в слотах `5` и `6` с количеством 16 и 1. |

В этом опыте разделение сохранило содержимое NBT обеих частей. Независимость копий вложенного NBT при последующем редактировании отдельно не проверял.

## 4. Сундук, броня и эндер-сундук

Из обычного инвентаря перенёс стек из 6 шерсти в верхнюю левую ячейку одинарного сундука, а кирку — в нижнюю правую. Прочитал `Level.TileEntities[].Items` из файлов `region/r.*.mca` через `tools/anvil_1710.py` и `nbtlib`. Контрольный сундук определил по обоим стекам:

```text
Items=[{Slot: 0b, id: 35s, Count: 6b, tag: {display: {Name: "S08-Red"}}, Damage: 14s}, {Slot: 26b, id: 257s, Count: 1b, Damage: 37s}]
```

В `Data.Player.Inventory` железные ботинки сохранились как `{Slot: 100b, id: 309s, Count: 1b, Damage: 2s}`. Железный шлем сохранился как `{Slot: 103b, id: 306s, Count: 1b, Damage: 3s}`.

Эндер-сундук записал ведро в отдельный список `Data.Player.EnderItems`. Первый замер дал `{Slot: 0b, id: 325s, Count: 1b, Damage: 0s}`. После переноса в нижнюю правую ячейку второй замер дал `Slot: 26b` при тех же `id`, `Count` и `Damage`.

## 5. OpenComputers и реестр Forge

В мире `S08-forge-items` игра выдала `OpenComputers Manual`. Положил книгу в первый слот панели и сопоставил её числовой ID с записью предмета из `FML.ItemData` по [формату S02](../contracts/blocks.md). Затем переименовал книгу на наковальне и повторил чтение сохранения:

```text
До:    {Slot: 0b, id: 4096s, Count: 1b, Damage: 98s}
После: {Slot: 0b, id: 4096s, Count: 1b, tag: {RepairCost: 2, display: {Name: "S08-OC-Manual"}}, Damage: 98s}
Registry: ['OpenComputers:item']
```

В этом мире ID `4096` соответствует `OpenComputers:item`. После переименования `id`, `Count`, `Damage` и запись реестра совпали. В `tag` появились Int `RepairCost` и вложенное имя.

На отдельной копии мира `S08-forge-missing` временно убрал JAR OpenComputers. Forge показал предупреждение о 80 отсутствующих записях блоков и предметов и сообщил, что при подтверждении автоматически создаст резервную копию перед загрузкой с удалением. После подтверждения `Yes` и сохранения сравнил рабочий `level.dat` с `level.dat` внутри созданного ZIP:

| Поле | Копия мира после загрузки без мода | Резервная копия до удаления |
| --- | --- | --- |
| `Data.Player.Inventory`, слот `0` | `EMPTY` | Книга с `id=4096s`, `Count=1b`, `Damage=98s`, `RepairCost: 2` и именем `S08-OC-Manual` |
| Записи предмета с ID `4096` в `FML.ItemData` | `[]` | `['OpenComputers:item']` |

Имя архива в этом прогоне — `S08-forge-missing-20261120-015613.zip`. Проверка касается записи предмета в `ItemData`. Повторную выдачу того же числового ID Forge не проверял.

## 6. Сетевой Slot протокола 5

Запустил проверенный ванильный сервер на Java `1.8.0_51`, адресе `127.0.0.1:25565`, в offline-mode. Консоль показала `Done (0.664s)`. Отправил handshake с protocol `5` и next state `2`, затем Login Start. Для чтения фреймов использовал функции из `tools/probe_s04.py`.

Первый сеанс `S08Wire` подтвердил пустой слот. Сервер принял `give`, но подходящий `Set Slot` (`0x2F`) в выводе не зафиксировал. Затем вошёл под тестовым профилем `S08Seed` и разобрал начальный `Window Items` (`0x30`). Наблюдение по целевому стеку совпало с шерстью из слота `0` одиночного мира после проверки предела:

```text
TX id=0x00 frame=0f 00 05 09 31 32 37 2e 30 2e 30 2e 31 63 dd 02
TX id=0x00 frame=09 00 07 53 30 38 53 65 65 64
RX id=0x02 body_length=46
WINDOW ITEMS: 0 45
STACK: 36 35 64 14 51 1f8b {display: {Name: "S08-Red"}}
EMPTY: (0, 'ffff') count= 44
```

| Поле | Наблюдение |
| --- | --- |
| Окно и длина списка | Окно `0`, 45 записей |
| Пустой сетевой Slot | Два байта `ff ff`. Всего 44 пустые записи. |
| Сетевой индекс заполненного слота | `36`. Соответствует первой ячейке панели, записанной в NBT с `Slot=0`. |
| Значения стека | `id=35`, `Count=64`, `Damage=14` |
| Полезная нагрузка NBT | 51 сжатый байт, сигнатура gzip `1f 8b`, после распаковки `{display: {Name: "S08-Red"}}` |

В живой сессии подтверждён `Slot` внутри `Window Items`. Пакет `Set Slot`, сетевой обмен Forge и совместимость с Horizon 26.3 остаются без проверки в этом прогоне.
